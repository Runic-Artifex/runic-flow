Standalone implementation specification · revision 2

Reusable application mechanics without reusable product policy.

This document is the complete build specification for a ViewModel-first flow library: navigation, typed dialogs, coordinated operations, and multi-step workflows. It deliberately assumes no access to any existing application or private source tree. An implementation team can derive the projects, public contracts, state machines, diagnostics, generators, adapters, tests, and release gates from this file alone.

01 · Scope and invariants

Mechanics only; policy stays with the application

“MUST”, “SHOULD”, and “MAY” are normative. The runtime MUST be usable in POCO tests with fake presenters and no browser, DOM, server, windowing toolkit, frontend framework, or reflection-based discovery.

Hard invariants

  • No global service locator or static “current View”.
  • No runtime assembly scanning.
  • No public HTML, DOM, component, window, brush, template, dispatcher, or framework types.
  • No untyped result protocol for dialogs or workflows.
  • No arbitrary object-graph serialization.

Supported baseline

  • net10.0 runtime and sample projects.
  • Nullable enabled; implicit usings disabled in libraries.
  • Warnings as errors, deterministic builds, package lock files.
  • Native AOT and trimming are release gates, not best-effort modes.
  • Thread-safe service entry points.

Explicit non-goals

  • A router that parses arbitrary web URLs.
  • A visual component library or CSS system.
  • Distributed workflow orchestration.
  • Undo/redo of business mutations.
  • Automatic persistence of ViewModels.
  • A replacement for framework command/binding systems.
Dependency direction: Flow depends on the CsWebUi.MVVM abstractions and Microsoft.Extensions abstractions. Frontend and MVVM-framework integrations depend on Flow. Flow never references an integration package.

03 · Shared contracts

Small immutable values and one ownership model

All key types are readonly string-backed record structs. Their public constructors validate non-empty, trimmed, ordinal identifiers containing ASCII letters, digits, ., -, _, or /; maximum length is 128. Equality and registry comparison are ordinal and case-sensitive.

Content session

An internal FlowContentSession owns exactly one IServiceScope, ViewModel instance, lifetime cancellation source, optional presenter lease, and child-session collection. Its public descriptor exposes session ID, logical contract, ViewModel as object plus its declared Type, and immutable metadata. The object is heterogeneous presentation data—not an untyped result channel.

Factory rule

Registrations store a closed factory delegate. The default delegate resolves the declared ViewModel from the new session scope using GetRequiredService<T>(). Generated registration MAY add the ViewModel to DI. Activator.CreateInstance, Type.GetType, constructor reflection, and assembly scanning are forbidden supported paths.

Disposal rule

Teardown order is children in reverse creation order, presenter lease, ViewModel if independently owned, then scope. Prefer IAsyncDisposable over IDisposable; never invoke both on one object. A DI-resolved ViewModel is scope-owned and MUST NOT be disposed separately. Every resource uses an interlocked exact-once guard.

Lifecycle fault boundary: callbacks before a presentation commit may abort and roll back. Callbacks after commit cannot roll back visible state; their errors are reported as FlowLifecycleException with stage and session metadata while the committed state remains authoritative.

Registration and startup validation

services.AddCsWebUiFlow(flow =>

04 · Navigation

Transactional ViewModel-first regions

A region is an independently serialized logical stack. Root regions are registered at startup. Nested regions are scoped beneath their owning content session and are shut down before that parent is disposed.

flow.Navigation(routes =>
{
    routes.AddRegion(new RegionKey("main"), options =>
        options.StartWith<HomeViewModel>());
    routes.AddPage<HomeViewModel>(
        new RouteKey("home"), new ViewContract("pages/home"));
    routes.AddPage<DetailsViewModel, DetailsRequest>(
        new RouteKey("details"), new ViewContract("pages/details"),
        retention: NavigationRetention.RetainInBackStack);
});

Normative transition order

  1. Check host state and cancellation; acquire the region’s async mutex. FIFO queuing is the default.
  2. Resolve the closed route and validate parameter type before creating a scope.
  3. Invoke the current entry’s INavigationGuard.CanLeaveAsync. Deny returns NavigationResult.Rejected; a fault aborts with current state unchanged.
  4. Create the target scope and ViewModel; call typed initialization, then ActivatingAsync. Any failure disposes the target session and leaves current state unchanged.
  5. Call INavigationRegionPresenter.PresentAsync. The adapter MUST either keep the old content intact on failure or restore it before throwing. The returned lease represents the rendered target.
  6. Perform the no-fail in-memory stack mutation and publish one immutable snapshot notification. This is the commit point.
  7. Call old DeactivatingAsync/DeactivatedAsync, then target ActivatedAsync. These are post-commit notifications; faults do not reverse the stack.
  8. Dispose entries removed by the transition. Release the mutex. If multiple post-commit callbacks failed, throw one FlowLifecycleException containing all ordered inner failures.

Retention

RetainInBackStack keeps the scope and ViewModel alive while stacked. RecreateOnBack stores route and parameter in memory, disposes on leave, and creates a fresh session when revisited. Parameters are never automatically serialized. Default: retain.

Concurrency

NavigationConcurrency.Queue is FIFO. RejectWhileBusy returns Busy without waiting. Cancellation while queued removes that request. A lifecycle callback that navigates the same region throws FlowReentrancyException; it may enqueue work through INavigationContinuation for execution after unlock.

History + deep links

The base engine owns logical history. A web adapter maps browser entries to route keys and generated parameter codecs. A popstate event requests Back/Reset; it never mutates Flow’s stack directly. Unknown or invalid deep links are handed to a consumer fallback policy.

Failure resolution: presenter failure is pre-commit and rolls back. Disposal failure is post-commit and is reported without resurrecting removed entries. Host shutdown bypasses user guards, rejects new navigation, cancels queued work, and tears down every region in reverse creation order.
05 · Typed dialogs

Exactly-once conversations with explicit outcomes

A dialog registration closes over ViewModel, request, and result types. Modal, modeless, route-backed, popover, and native-window display are presenter policies selected by a logical presenter key.

flow.Dialogs(dialogs =>
    dialogs.Add<ConfirmViewModel, ConfirmRequest, Decision>(
        new DialogKey("confirm"), new ViewContract("dialogs/confirm"),
        new PresenterKey("modal")));

DialogOutcome<Decision> outcome = await dialogs.ShowAsync<
    ConfirmViewModel, ConfirmRequest, Decision>(
        request, cancellationToken);

public enum DialogOutcomeKind { Completed, Cancelled, Dismissed }
public readonly record struct DialogOutcome<T>(DialogOutcomeKind Kind, T? Value)
{
    public static DialogOutcome<T> Completed(T value);
    public static DialogOutcome<T> Cancelled();
    public static DialogOutcome<T> Dismissed();
}

public interface IDialogController<TResult>
{
    bool IsCompletionRequested { get; }
    ValueTask<bool> CompleteAsync(TResult result, CancellationToken cancellationToken = default);
    ValueTask<bool> CancelAsync(CancellationToken cancellationToken = default);
    ValueTask<bool> DismissAsync(CancellationToken cancellationToken = default);
}

Completed, Cancelled, and Dismissed are ordinary typed outcomes. Initialization, presenter, lifecycle, or close failures are exceptions and MUST NOT be disguised as a dismissal. TResult may be nullable; therefore outcome kind—not null—indicates completion. Cleanup after caller cancellation uses the session lifetime token rather than the already-cancelled caller token.

Open, complete, and close ordering

  1. Create a child session beneath the current parent session when one exists; otherwise create a root dialog session.
  2. Resolve ViewModel and scoped IDialogController<TResult>, initialize with TRequest, run ActivatingAsync, then open through the selected presenter.
  3. Commit the presenter lease, mark Open, run ActivatedAsync, and await a completion request. Nested dialogs are allowed because each receives its own session and controller.
  4. The first controller, adapter, cancellation, or shutdown request wins an interlocked completion race. Later requests return false and have no side effects.
  5. If the ViewModel implements IDialogCloseGuard, consult it for Complete/Cancel/Dismiss. A denial clears the pending claim so a later request may retry. Shutdown bypasses the guard.
  6. After acceptance, disable action dispatch, close all child dialogs in reverse order, run DeactivatingAsync, ask the presenter lease to close, run DeactivatedAsync, then dispose the session. Only after teardown succeeds does ShowAsync complete with the accepted outcome.

Actions and keyboard semantics

A registration or ViewModel may expose immutable FlowAction values. At most one visible enabled action may be IsDefault and at most one IsCancel; validation rejects ambiguity. Adapters map Enter/Escape and focus behavior, then dispatch the logical ActionKey. They MUST NOT infer completion from button labels or CSS variants.

Cancellation semantics

The caller token requests Cancelled; it does not abruptly abandon cleanup. If the close guard denies cancellation, the Show task continues and the caller can use a separate timeout. Host shutdown always closes. Presenter disconnection requests Dismissed. A presenter fault before open faults Show; a close fault after an accepted result is reported as a lifecycle exception and the accepted outcome remains available in exception metadata.

Scope rule: a dialog is owned by its parent session, not by a global window. Closing a page closes its dialogs; closing a parent dialog closes nested dialogs. Parent teardown waits for child teardown, with bounded shutdown timeout controlled by host options.

Normative execution order

  1. Validate request and acquire its slot policy. Create operation ID, linked cancellation token, and optional timeout token.
  2. Publish Queued then Starting. If a presenter is requested, resolve it and call Show before work. A missing key fails startup validation; a Show failure prevents work.
  3. Publish Running, invoke the delegate once, and accept thread-safe progress reports. Fraction MUST be finite and in 0…1; values may decrease because the work—not the View—owns target progress.
  4. On success publish Succeeded. On linked cancellation publish Cancelled and RunAsync throws OperationCanceledException. On another exception publish Faulted and preserve the original exception and stack.
  5. Hide/dispose presentation, publish Finished, remove monitor state according to retention options, dispose cancellation sources, release the slot, and then return or throw.

Monitoring

IOperationMonitor exposes immutable snapshots and a subscription API from the base MVVM runtime. Snapshots contain logical metadata, timestamps, state, latest progress, and cancellation availability—never the work delegate or exception details intended for logs.

Error precedence

A work exception is primary. Hide/disposal faults are emitted as cleanup diagnostics and attached to FlowCleanupException metadata without masking the work exception. If work succeeded and cleanup alone failed, RunAsync throws FlowCleanupException.

Command adapters

Toolkit and ReactiveUI integrations build commands that call the same runner, project CanExecute from slot state, expose cancellation, and route exceptions to an injected IOperationErrorHandler. The default handler logs and rethrows on the configured host error boundary; it never silently consumes faults.

Presentation isolation: inline, overlay, page, toast, and “none” are logical presenter keys. Animation and interpolated progress belong to the frontend. Operations never navigate automatically; a consumer callback may request navigation after successful cleanup.
07 · Workflows

A typed step engine—not a wizard control

A workflow is an immutable, typed graph of interactive steps. A wizard is one possible renderer. The engine supports linear and conditional flows, backtracking, custom actions, validation, finish/cancel outcomes, and optional consumer-defined checkpoints.

flow.Workflows(workflows =>
    workflows.Add<SetupContext, SetupResult>(
        new WorkflowKey("setup"), schemaVersion: 1,
        builder => builder
            .AddStep<WelcomeViewModel>(
                new StepKey("welcome"), new ViewContract("setup/welcome"))
            .AddStep<OptionsViewModel>(
                new StepKey("options"), new ViewContract("setup/options"),
                includeWhen: static context => context.CanChooseOptions)
            .AddStep<ReviewViewModel>(
                new StepKey("review"), new ViewContract("setup/review"))
            .StartWith(new StepKey("welcome"))
            .FinishWith(static context => new SetupResult(context.Selection))));

WorkflowOutcome<SetupResult> result = await workflows.RunAsync<
    SetupContext, SetupResult>(new WorkflowKey("setup"), context, cancellationToken);

Definition

Contains key, schema version, typed context/result types, unique steps, start step, transitions, include predicates, retention, action definitions, result factory, and optional checkpoint codec/store. The builder emits an immutable definition and rejects unreachable steps and edges to missing keys.

Step contracts

A step ViewModel may implement IFlowInitializable<TContext>, activation lifecycle, IWorkflowStepValidator<TContext>, and IWorkflowStepCommit<TContext>. It need not inherit a base class. Validation returns structured issues; ordinary validation failure is not an exception.

Outcome

WorkflowOutcome<TResult> is Completed, Cancelled, or Abandoned. Definition/lifecycle/presenter faults throw. Nullable results are valid. Finish is the only route to Completed; browser disconnect or parent teardown is Abandoned unless host shutdown marks cancellation.

History

Visited history records actual step keys after predicates and redirects. Back follows visited history, not static graph order. A removed conditional step is skipped and disposed. Default retention is one live current step plus retained context; consumers opt into retaining visited step scopes.

Actions

Built-ins use stable keys back, next, finish, and cancel. Custom actions return Stay, GoTo, Finish, or Cancel. All share FlowAction metadata, are serialized per workflow session, and cannot mutate runtime state directly.

Context safety

The context is application-owned mutable or immutable state. The engine does not clone or roll back it. Step commit callbacks must define their own transaction semantics. Documentation MUST warn that Back changes navigation history, not business side effects.

Forward transition order

  1. Acquire the workflow-session mutex; reject direct same-session re-entrancy.
  2. Evaluate current step validation. On Invalid, publish issues and return Stayed without running leave hooks.
  3. Run current step commit and pre-deactivation hooks. A fault aborts with current presentation intact.
  4. Resolve the requested edge; repeatedly skip excluded steps; detect loops with a per-transition visited set and fail with WorkflowGraphException.
  5. Create/restore target session, initialize it with the same typed context, run pre-activation, and present it. Failure disposes a new target and leaves current active.
  6. Commit current key/history/progress in one snapshot, then run post-deactivation/post-activation and dispose the old step if not retained.

Finish, cancel, and checkpoint rules

  • Finish validates and commits the current step, executes the typed result factory exactly once, closes presentation, publishes Completed, then disposes. A result-factory fault leaves the workflow current so the application may retry unless the configured fault policy closes it.
  • Cancel consults IWorkflowCancelGuard<TContext>; a denial stays. Host shutdown bypasses the guard. Cancellation never calls the result factory.
  • A checkpoint contains workflow key, schema version, current step key, visited keys, and opaque consumer payload bytes. It MUST NOT contain ViewModel instances, services, commands, delegates, or presenter state.
  • The consumer supplies IWorkflowCheckpointCodec<TContext> and IWorkflowCheckpointStore. Serialization contexts must be source-generated for AOT. Encryption, authentication, migration, expiration, and storage are consumer responsibilities.
  • Restore validates key/version and step existence before creating a scope. A consumer migration delegate may transform older payloads. Invalid checkpoints fail explicitly; they never silently start over.

Presenter atomicity

For replacement, an adapter MUST finish constructing/binding target content before removing current content. If activation fails, it restores or retains current content. Visual animation may continue after commit only if it cannot reject the transition.

Thread/dispatch

The runtime does not capture SynchronizationContext. Adapters marshal DOM/frontend work through the core IUiDispatcher. Lifecycle callbacks run on the caller/continuation scheduler and MUST NOT assume a UI thread.

Event authority

Frontend events request engine actions using session ID plus logical action. The engine rejects stale session IDs. Adapters never directly edit stacks, mark operations complete, or finish workflows.

Mapping validation: each registered ViewContract required by enabled features MUST have exactly one mapping in the selected frontend adapter. Duplicate mappings fail registration. Missing mappings fail host validation before the first user interaction and name both contract and ViewModel type.

Native AOT rules

  • No runtime assembly scanning, dynamic assembly emission, expression compilation, dynamic, Type.GetType(string), unbounded MakeGenericType, or reflection-selected constructors.
  • DI activation uses closed registrations and source-emitted generic calls. JSON for deep links/checkpoints uses consumer-supplied JsonTypeInfo<T> or codecs; never options-only reflection serialization.
  • Every package build runs trim analysis. The AOT smoke app references packed NuGets, publishes with PublishAot=true, PublishTrimmed=true, and treats IL2xxx/AOT warnings as errors.
  • Generator output is stable across machine paths and cultures. Snapshot tests normalize line endings and verify incremental invalidation.

Runtime diagnostics

Logging

Use structured ILogger events with stable IDs grouped by feature. Include session ID, logical key, stage, outcome, duration, and exception. Never log parameters, dialog results, context payloads, or user copy by default.

Tracing

ActivitySource name CsWebUi.MVVM.Flow. Activities: flow.navigate, flow.dialog, flow.operation, flow.workflow, and flow.present. Propagate parent context into nested sessions.

Metrics

Meter of the same name. Counters for transitions/outcomes/faults; histograms for duration and queue wait; observable gauges for active sessions and operations. Tags use bounded logical keys, never arbitrary messages.

Public exception types: FlowRegistrationException, FlowValidationException, FlowLifecycleException, FlowCleanupException, FlowReentrancyException, FlowPresenterException, OperationBusyException, and WorkflowGraphException. Every exception exposes feature, logical key, session ID when available, and lifecycle stage as typed properties.

10 · Verification matrix

State machines are the product

Test clock

Timeout, duration, and retention code depends on TimeProvider. Tests use FakeTimeProvider; no wall-clock delays are accepted in unit tests.

API approvals

Each assembly has a reviewed public API baseline. Breaking changes require a major version and migration note. Binary compatibility is checked against the previous stable package.

Leak checks

Weak-reference tests prove released scopes/ViewModels/leases are collectable. Adapter integration tests assert listener, observer, timer, and DOM/component counts return to baseline.

Definition of done for each feature

  1. Public contract documented with success, rejection, cancellation, fault, and shutdown semantics.
  2. POCO contract tests cover lifecycle ordering and disposal.
  3. Generator/registration path has compile-time and startup diagnostics.
  4. At least two frontend styles—one client component adapter and HTMX/server template adapter—pass the same scenario.
  5. Packed-package Native AOT smoke passes with zero warnings.
  6. API approval, XML docs, sample, migration note, diagnostics reference, and performance baseline are committed.
11 · Compatibility and evolution

Stable semantics before convenience

The first stable release freezes key equality, lifecycle commit boundaries, outcome kinds, disposal ownership, exception categories, diagnostic IDs, and serialized checkpoint envelope. Convenience overloads may grow without changing those rules.

Semantic versioning

Removing/renaming public APIs, changing callback order, changing default retention/concurrency, altering result meaning, or changing key comparison requires a major version. New optional metadata and overloads are minor changes.

Framework independence

BCL and base MVVM contracts remain the baseline. CommunityToolkit and ReactiveUI support stays in integrations. Their major upgrades may release independently only if the core package range remains honest and conformance tests pass.

Persistence

Checkpoint envelopes carry library format version plus consumer workflow schema version. The library supports reading the previous envelope version for one major release; consumer payload compatibility remains the consumer’s responsibility.

Splitting later

If Navigation, Dialogs, Operations, or Workflows become separate packages/repositories, retain existing namespaces and type identities where possible. Use type forwarding during a major transition; never force consumers to rename logical keys.

Performance budgets

After DI warm-up, registry lookup and snapshot reads allocate no transient collections. A simple transition adds only the new scope/session/presenter resources. Publish baseline throughput, allocation, and AOT binary-size deltas at release.

Security

Treat deep-link parameters, HTMX action posts, checkpoint bytes, and session IDs as untrusted. Validate codecs, reject stale/unknown sessions, require host CSRF/auth policy, bound payload sizes, and avoid secrets in logs/metrics.

Release acceptance

  • A clean clone builds, tests, packs, and produces the AOT smoke executable without private feeds, machine-local files, or undocumented setup.
  • Every public type has XML documentation; every lifecycle interface links to an ordered state table and fault semantics.
  • All contract, generator, adapter, stress, leak, package, trimming, and AOT suites pass on supported CI platforms.
  • Runtime has no reflection-discovery path and no trim/AOT suppression without an issue, justification, and dedicated test.
  • Angular and HTMX reference adapters are complete; React, Vue, and Svelte pass the conformance kit before their packages claim support.
  • Two unrelated sample domains use the same runtime without custom lifecycle, scope, typed-result, or cancellation plumbing.
  • Public API and diagnostic baselines are approved; changelog states compatibility guarantees and known limitations.
